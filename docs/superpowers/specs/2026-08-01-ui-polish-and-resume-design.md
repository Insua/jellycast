# 状态栏配色、首页顶部留白、播放进度持久化 设计文档

> 状态:已定稿(2026-08-01)
> 前置:v7(首页静默定时刷新)已合入 master。
> 本文覆盖三个真机使用后提出的改动。音频缓存子系统**不在本文范围**,它有自己的 spec。

---

## 1. 状态栏图标与浅色主题撞色

### 现象

界面是浅色的,但顶部系统状态栏的电池、信号、时间是**浅色(白色)图标**,在浅色背景上几乎看不清。

### 根因

`app/src/main/res/values/themes.xml`:

```xml
<style name="Theme.JellyCast" parent="android:Theme.Material.NoActionBar">
    <item name="android:windowBackground">@android:color/black</item>
</style>
```

`android:Theme.Material.NoActionBar` 是**深色**主题。系统据此判定"这个应用背景是深的",于是画浅色状态栏图标。而应用实际渲染的是 Compose 的浅色主题 —— 判定依据和实际显示对不上。

代码里**没有任何地方**设置过状态栏外观:全项目搜不到 `isAppearanceLightStatusBars`、`WindowCompat`、`enableEdgeToEdge`。

顺带一个同源问题:`windowBackground` 是纯黑,而应用主题是浅色 —— 冷启动时 Compose 内容渲染出来之前会**黑闪一下**。

### 方向

由应用**显式声明**状态栏图标外观,而不是让系统从 XML 主题去猜。这个应用是**只有浅色主题**的(用户已多次明确否决深色),所以状态栏图标固定为深色。

同时把 `windowBackground` 改成与 Compose 浅色主题一致的颜色,消除启动黑闪。

**不引入 `enableEdgeToEdge()`。** targetSdk 36 在 Android 15+ 上本来就是强制 edge-to-edge,而 v5 已经把 inset 处理调好了(`HomeScreenInsetTest` 是那次的产物)。为了改图标颜色去动 inset 体系,风险远大于收益。

### 验收

- 浅色界面下,状态栏的电池 / 信号 / 时间是**深色**图标,清晰可辨
- 冷启动不出现黑屏闪烁

## 2. 首页顶部留白过多

### 现状测量

首页第一行内容之上压着四层:

| 层 | 高度 |
|---|---|
| 状态栏 inset(由 `Scaffold` 提供) | 约 24dp |
| `Column(Modifier.padding(vertical = 8.dp))` | 8dp |
| `TopAppBar`(标题「JellyCast」+ 搜索 + 账户) | 64dp |
| `TabRow`(首页 / 我的最爱) | 48dp |
| **合计** | **约 144dp** |

问题出在那个 64dp 的 `TopAppBar`:它整整占掉一行,而里面只有一个**静态的应用名**和两个图标。应用名对用户没有信息量 —— 他知道自己打开的是哪个 App。

### 方向

**去掉独立的标题栏,把两个图标并进 `TabRow` 那一行**:标签靠左,搜索与账户图标靠右,一行搞定。

```
┌──────────────────────────┐
│ ▔▔ 状态栏 ▔▔             │
│ 首页  我的最爱     🔍 👤 │
│ ──────                   │
│ 继续收听                 │
│ [封面] [封面] [封面]     │
└──────────────────────────┘
```

省下 `TopAppBar` 的 64dp 加上 `Column` 的 8dp,顶部 chrome 从约 144dp 降到约 72dp —— **减半**。

标签行本身保留 `TabRow` 的选中指示器,切换行为不变。

### 验收

- 首页第一行内容距屏幕顶端的距离显著减小(以真机/模拟器截图为证)
- 搜索、账户两个入口仍然可点、语义不变
- 标签切换行为不变

## 3. 播放进度持久化:打开就能接着听

### 用户要的是什么

> 像网易云音乐那样,把当前的播放进度条给缓存住,即使播放的哪个片、哪一个季、哪一集的进度,一直给缓存住,下次打开 app 后,直接就加载这个进度了,点击播放就可以了。

现状:冷启动后迷你播放条是空的,必须先进首页 → 找到「继续收听」→ 点进去,才能开始播。

### 方向

在本地持久化**一条**「上次在播什么」的记录,冷启动时把播放器**装填好但不播放**。

#### 存什么

一条窄记录,只包含两件事所需的字段:**恢复播放**(条目 id、位置)与**渲染迷你条**(标题、副标题、封面 tag、总时长)。

**刻意不持久化整个 `MediaItem`。** 那是领域模型,字段会随功能演进增删;把它直接序列化进存储,等于让每一次模型改动都变成一次存储格式变更。持久化记录是独立的、窄的、只增字段的。

存在 DataStore 里(单条 JSON),不引入 Room 迁移。

#### 什么时候写

复用播放中**每 10 秒的进度心跳**那个时机 —— 那里同时拿得到当前条目和绝对位置。播放停止时再写一次收尾值。

#### 什么时候读、读了以后做什么

冷启动时读出来,然后:

- 把条目放进播放队列
- 让迷你播放条按「已暂停 + 已有进度」的样子显示出来

**三条硬约束:**

1. **绝不自动开始播放。** 打开 App 就自顾自出声是让人恼火的行为,也白耗流量。
2. **绝不启动前台服务、绝不贴通知。** 什么都没在播的时候通知栏不该有东西。
3. **绝不发网络请求。** 恢复必须在断网、未登录、服务器不可达的情况下同样能完成 —— 它读的是本地记录。

点下播放按钮时,才走正常的播放路径,起点用记录里的位置。

#### 续播位置用本机的,不去服务器取

**已确认的取舍。** 本机记录的优点是冷启动零延迟、断网可用;缺点是如果你在电视上又看了几集,点迷你条会从**手机上次**的位置开始,而不是电视的位置。

跨设备的最新进度仍然可以从首页「继续收听」进入 —— 那条路径读的是服务端,而且 v7 已经让它在回到首页时自动刷新。两条路径各自的语义是清楚的:**迷你条 = 这台设备上次听到哪**,继续收听 = 服务端认为你听到哪。

#### 记录何时失效

- 换服务器 / 退出登录:记录清除(它属于某一个服务器的某一个条目)
- 条目在服务端已被删除:点播放时按既有的播放失败路径处理,不为它新增分支

### 验收

- 播放任意一集,杀掉进程重开 App:迷你播放条显示的就是那一集,进度条停在离开时的位置
- 点播放能从该位置续上
- 冷启动**不**自动播放、**不**出现通知、**不**发网络请求
- 断网冷启动同样能恢复出迷你条

## 4. 范围

**做:** 状态栏图标外观 + 启动背景色 · 首页顶部合并为一行 · 上次播放记录的持久化与恢复

**不做:**

- **音频缓存 / 预取** —— 独立子系统,有自己的 spec
- 深色主题(用户已多次明确否决)
- 恢复整个播放**队列**(只恢复当前条目;上一集/下一集仍由既有的按剧集顺序推进逻辑负责)
- 自动播放

## 5. 测试策略

| 改动 | 怎么验 |
|---|---|
| 状态栏图标外观 | 设备测试:在真实 Activity 上断言状态栏外观标志为「浅色背景 / 深色图标」。**这是平台行为,JVM 测不出**(v4 铁律) |
| 启动背景色 | 主题资源断言 + 截图 |
| 首页顶部 | 设备测试**测量**第一行内容的顶部偏移,并与改动前的基线对比 —— 沿用 `HomeScreenInsetTest` 的做法(那次正是靠像素测量发现顶部多出恰好一个状态栏高度的) |
| 持久化记录 | JVM 单测:写入时机、字段完整性、清除时机 |
| 恢复行为 | JVM 单测:冷启动恢复出迷你条;**断言恢复过程中没有创建任何 api client、没有启动服务**(沿用离线缓存那条用例的做法) |
| 「不自动播放」 | JVM 单测:恢复之后播放器仍处于未播放状态 |

**每条新测试都必须能对着未实现的代码失败。** 本仓库在最近几轮里反复出现"看着对但测不出任何东西"的空测试,每一条新用例都要用变异验证钉死。
