# 崩溃修复与功能可用性 设计文档

> 状态:已定稿(2026-07-28)
> 前置:v3(离线缓存 / 系统集成 / 浏览对齐)已合入 `feat/stability-and-web-parity`。
> 本文覆盖真机使用后暴露的崩溃与一批不可用的功能。

---

## 1. 为什么做这个

真机反馈,用户原话:「必须都不能闪退,这是最重要的」「所有的功能都得可点,可用」。

已定位根因的问题:

1. **播放带文本字幕的条目必崩。** 不是某一部剧的问题 —— 是**凡是有文本字幕轨的条目都会崩**。
2. 首页「我的媒体」的库卡片点了没反应。
3. 系统媒体控制只有下一集,没有上一集。
4. 默认选中的字幕是弹幕轨而不是真字幕。
5. 歌词高亮在重叠时间轴上基本失效,且轮询频率不足。

尚需证据的:进度条拖动不跟手、一加胶囊点开不显示播放时间、播放卡顿(用户希望有类似 web mobile 的缓冲)。

## 2. 崩溃的根因,以及它暴露的系统性问题

```kotlin
SubtitleTags.kt:12   Regex("""\{[^}]*}""")
                                      ↑ 未转义的右花括号
```

这个模式在 **OpenJDK 的正则引擎上合法**,在 **Android 14+ 的 ICU 引擎上是语法错误**。后果是连锁的:

1. `SubtitleTags` 是 `object`,正则在**静态初始化**里编译 → 抛 `ExceptionInInitializerError`
2. 那是 `Error` 而不是 `Exception`,`SubtitleRepository.load` 的 `catch (e: Exception)` **接不住**
3. 它穿透到 `PlayerViewModel` 里没有保护的 `viewModelScope.launch` → 进程被杀

### 系统性教训:纯 Kotlin 模块的"可离线单测"是有盲区的

`:core:subtitle` 被刻意设计成纯 JVM 模块,因为"解析是纯 Kotlin"。**但它跑在 Android 上,而 Android 的正则引擎和 JVM 不是同一个实现。** 421 个 JVM 单测全绿却在真机上必崩,原因就在这里 —— JVM 测试**结构上不可能**发现平台差异。

**因此本次追加一条铁律:凡是最终运行在 Android 上、且依赖平台 API 行为(正则、`Uri`、时间格式化、文本处理)的纯 Kotlin 模块,必须有一份在真机上跑的冒烟测试。** 不要求覆盖率,只要求"每个关键入口在真机上被调用过一次"。

### 防御纵深

单点修复不够。三层都要加:

| 层 | 措施 |
|---|---|
| 根因 | 转义正则;并把所有正则的编译从静态初始化挪到可捕获的位置 |
| 中间 | 字幕相关的失败捕获从 `Exception` 放宽到 `Throwable`(但 `CancellationException` 仍须重抛) |
| 兜底 | `viewModelScope.launch` 的字幕/网络分支加保护,任何 `Throwable` 都收敛成 UI 错误态而非崩溃 |

> ⚠️ 放宽到 `Throwable` 是有争议的 —— 它会吞掉 `OutOfMemoryError` 这类本该让进程死掉的错误。
> 取舍:**字幕是纯装饰功能,它的任何失败都不该影响播放**(这是 v1 就定下的铁律)。
> 仅限字幕路径放宽,不得推广到别处。`CancellationException` 必须继续传播。

## 3. 其余缺陷的根因

### 3.1 「我的媒体」点不进去

`JellyCastNavHost` 调用 `HomeScreen(...)` 时**没有传 `onLibraryClick`**,参数走了默认值 `= {}`。
而且路由表里根本没有"进入某个库"这条路由(只有 `library`、`library/series/{id}`、`library/collection/{id}`)。

需要:新增按库浏览的路由,并把回调接上。库内内容用 `/Items?parentId=<libraryId>`。

### 3.2 没有上一集

导航层有 4 处调用 `sessionViewModel.play(item, listOf(item))` —— **队列长度恒为 1**,
`hasPrevious()` 因此恒为 false。只有剧集详情页那一处传了真实的整季队列。

"下一集"看起来能用,是因为 `AutoPlayNextController` 会去 NextUp 补队列,与队列本身无关。

需要:从首页各分区播放时构造**有意义的队列** —— 继续收听/最近添加用该分区的列表,
下一集用 NextUp 列表。播放当前项时把同分区的其余项一并作为队列。

### 3.3 字幕默认选中弹幕

`PlayerViewModel` 在没有匹配到首选语言时取 `subtitleTracks.firstOrNull()`。
实测样本里 index 0 是外挂弹幕(3676 条),index 4 才是真字幕(774 条)。

需要:选轨时**降低弹幕类轨道的优先级**。可用信号:`IsExternal` 为 true 且标题含 danmu/弹幕、
或条目数异常多。选不出时宁可不显示字幕,也不要显示弹幕。

### 3.4 歌词高亮在重叠时间轴上失效

`SubtitleTimeline.indexAt` 是按"有序、不重叠"假设写的二分查找。弹幕轨大量重叠,
实测 3676 条里只有 **53 条**会被高亮。

即便修好选轨,普通字幕偶尔也有重叠(前后两句衔接处)。需要:让查找对重叠输入给出合理结果
(取覆盖当前位置且最晚开始的一条),而不是依赖不重叠假设。

### 3.5 轮询频率不足

500 ms 轮询漏掉 85% 的字幕行。歌词要跟得上朗读节奏,需要更高频率或改为
按下一行的边界调度。**注意功耗** —— 不能简单把间隔调到 50 ms 了事。

## 4. 尚需证据的三项

**不猜,先复现再定方案。**

- **进度条拖动不跟手** —— 怀疑与 seek 走"重新请求转码"的固有延迟 + 250 ms 去抖叠加有关,
  但也可能是 `durationMs` 或拖动手势本身的问题。
- **一加胶囊点开不显示播放时间** —— 怀疑 MediaSession 未持续发布
  `PlaybackState` 的位置/时长/速度,导致系统侧无法推算进度。
- **播放卡顿** —— 用户希望有 web mobile 那样的缓冲。

  ⚠️ **需要澄清一个误解:** 用户建议"模仿 web mobile 接受最低码率但不显示视频"。
  实际上 JellyCast 的 L1 已经**只接收音频**(132 kbps),比 web mobile 最低档视频流还省一个量级 ——
  服务端根本不传视频字节。所以卡顿**不是码率问题**。真正的嫌疑是:ExoPlayer 的缓冲参数从未配置过
  (用的是默认值),且每次 seek 都要等服务端重新起转码,那几秒空窗没有任何缓冲遮掩。
  方向应是**调缓冲策略**,不是降码率。

## 5. 诊断能力(本次新增)

真机调试的来回成本过高(无线调试配对多次失败、局域网与 Tailscale 路径不稳)。
**在 app 内加诊断日志导出**:崩溃与关键错误落盘到应用私有目录,设置页一键分享。

要求:
- 不得记录任何凭据(token、密码)、不得记录服务器地址的完整形式
- 有容量上限与轮转,不得无限增长
- 默认开启,但用户可关闭

## 6. 范围

**做:** 正则崩溃修复 + 三层防御 · `:core:subtitle` 真机冒烟测试 · 我的媒体路由 · 有意义的播放队列 ·
字幕选轨降级弹幕 · 重叠时间轴的歌词定位 · 提高歌词跟随精度 · 诊断日志导出 ·
进度条/胶囊/缓冲三项的复现与修复

**不做:** 弹幕渲染(把弹幕当弹幕显示是另一个产品功能,本次只是别把它当字幕) ·
深色主题 · 改播放页形态 · 离线下载

---

## 7. 验收标准

- **任何条目都不崩** —— 包含文本字幕、多音轨、外挂弹幕、mp4/hevc 容器的条目全部可播
- `:core:subtitle` 的每个解析入口在真机上被执行过至少一次
- 首页「我的媒体」的库卡片可进入并列出内容
- 系统媒体控制上一集/下一集都可用且行为正确
- 默认字幕不是弹幕
- 歌词跟随不漏行
- 诊断日志可导出,且不含任何凭据
- 全部既有测试保持绿
