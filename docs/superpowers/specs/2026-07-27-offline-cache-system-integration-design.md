# 离线缓存、系统集成与浏览层对齐 设计文档

> 状态:已定稿(2026-07-27)
> 前置:v1、v1.1(分页搜索)、v2 稳定性修复已完成。本文覆盖 v2 未做完的部分与真机反馈的新问题。

---

## 1. 为什么做这个

真机使用后的反馈,按严重程度:

1. **没开 Tailscale 时进 App 直接闪退。** 应用**零缓存** —— Room 里只有进度补报队列。
   v1 设计文档写的是「`:core:database` Room:缓存与进度」,但缓存那一半从未实现。
   没网就什么都没有,这是产品级缺陷,不是边角。
2. **锁屏、通知栏、蓝牙上没有上一集/下一集。** 根因是播放器**只持有单个条目**
   (全项目只有 `setMediaItem`,从无 `setMediaItems`),`hasNextMediaItem()` 恒为 false,
   Media3 因此不生成这些按钮。
3. **锁屏与通知内容空白。** 从未给 `MediaItem` 设过 `MediaMetadata`。
4. 浏览层与 Jellyfin Web mobile 差距明显;缺收藏、排序筛选、合集、已看标记。
5. 应用还在用 Android 默认图标。

---

## 2. 范围

**做:** 离线缓存与逐步刷新 · L3 seek 修复 · seek 防抖 · 媒体元数据 · 上下一集(通知/锁屏/蓝牙/迷你条)· 应用图标 · 浏览层对齐 Web mobile · 收藏 · 排序筛选 · 合集 · 标记已看未看 · 仓库地址清理

**不做:**
- **章节跳转** —— 用户已确认砍掉。Jellyfin 章节服务于视频跳转,音频场景价值低。
- **离线下载** —— 本次只做**列表缓存**,不做音频下载。
- **深色主题** —— 用户明确要求保持浅色,尽管 Web mobile 是深色。
- **改播放页形态** —— 仍是大封面 + 歌词式字幕。

## 3. 架构决策

### 3.1 缓存:Room 条目缓存 + stale-while-revalidate

**问题:** 现在是「调 API → 显示」,无网即空白。

**方案:** 在 `:core:database` 增加条目缓存表,`:core:network` 之上加一层仓储:

```
ViewModel → Repository → ① 立刻发射缓存(可能是旧的)
                       → ② 后台请求网络
                       → ③ 成功则写库并发射新数据;失败则保留缓存并标记「离线」
```

发射的是 `Flow`,UI 订阅后自然拿到"先旧后新"。**这是本次最大的架构改动** ——
所有列表类 ViewModel 的取数方式都要改。

**缓存内容:** 首页三个分区、媒体库列表、剧集详情(季/集)、库列表(UserViews)。
**不缓存:** 播放源 URL(有时效性、带 token)、字幕(体积大且按需)。

**失效策略:** 不做 TTL 过期删除 —— 缓存是"上次看到的样子",过期也比空白强。
只在成功刷新时覆盖。提供设置项手动清空。

**封面图:** Coil 已有内存缓存,需显式开启**磁盘缓存**并指定容量上限。

### 3.2 离线态的 UI 契约

| 状态 | 表现 |
|---|---|
| 有缓存 + 网络正常 | 直接显示,后台刷新,用户无感 |
| 有缓存 + 网络不可用 | **立刻显示缓存**,顶部一条可关闭的提示「离线,显示的是上次内容」 |
| 无缓存 + 网络不可用 | 显示「无法连接服务器」+ 重试按钮。**不得崩溃** |
| 离线时点播放 | 明确提示「需要连接服务器才能播放」,不静默失败 |

**铁律追加:网络不可用绝不允许导致崩溃。** 所有网络调用的失败路径必须收敛到上述状态之一。

### 3.3 上一集/下一集:用 ForwardingPlayer 暴露命令,不伪造播放列表

**约束回顾:** 服务端返回 `Accept-Ranges: none`,所以 seek 实现为"带新 `startTimeTicks`
重新请求 + prepare",播放器每次只持有一个条目。这个架构不能推翻。

**方案:** `SeekInterceptingPlayer` 已经是 `ForwardingPlayer`。让它:
- 覆写 `getAvailableCommands()`,把 `COMMAND_SEEK_TO_NEXT_MEDIA_ITEM` /
  `COMMAND_SEEK_TO_PREVIOUS_MEDIA_ITEM` 按 `PlayQueue` 的真实状态声明出来
- 覆写 `seekToNextMediaItem()` / `seekToPreviousMediaItem()`,委派给 `PlayQueue` + 引擎

这样通知栏、锁屏、蓝牙、车机**同时**获得上下一集,而无需给 Media3 塞一个假的播放列表
(假列表会与"每次重新 resolve"的机制冲突)。

> ⚠️ 注意 `seekToPrevious()`(不带 MediaItem 后缀)语义不同 —— 它在非直播、
> 播放位置超过阈值时是"回到本集开头"。v1 已为它做过拦截,本次不得破坏。

### 3.4 媒体元数据

给交给播放器的 `MediaItem` 设完整 `MediaMetadata`:标题(集名)、副标题(剧名 · SxxExx,
复用 `displaySubtitle`)、封面(`artworkUri`)。这是锁屏、通知、**OPPO 流体云**、
车机显示的共同前提 —— 流体云对媒体场景接管标准 MediaSession 通知,不需要厂商 SDK。

### 3.5 L3 seek 空操作

L3 URL 带 `static=true`,服务端因此**静默忽略 `startTimeTicks`**,结果是进度条跳了、
音频从头放 —— 比报错更糟,因为用户看不出来。

**方向:** L3 走非 static 的转码 URL 以支持 `startTimeTicks`;若实测服务端仍不支持,
则在该路径下**明确禁用 seek 并告知用户**,而不是假装成功。**实现前必须对真实服务器实测确认。**

### 3.6 浏览层对齐(保持浅色)

参照的是**结构与信息层级**,不是配色。顶部栏 + 首页/我的最爱标签;新增「我的媒体」库入口
(`GET /UserViews`);继续收听改 16:9 + 已听进度条;最近添加按库分组 + 未看数角标
(`UserItemDataDto.UnplayedItemCount`)。

### 3.7 新增功能的接口

一律以 `docs/jellyfin-openapi.json` 为准,逐个 `jq` 核对。**Jellyfin 对错误大小写的查询参数
静默忽略**,v1 期间已查出 6 处此类错误。收藏、已看标记、排序筛选、合集分别对应
`/UserFavoriteItems`、`/UserPlayedItems`、`/Items` 的 `sortBy`/`filters`、
`includeItemTypes=BoxSet` —— **具体路径与参数名实现时核对,本文不做权威。**

## 4. 测试策略

v2 建立的端到端脚手架(`:app/src/androidTest`,真 ExoPlayer + 真 MediaSession + 真服务器)
是本次的基础设施,必须扩展而非绕过。

**必须新增的端到端场景:**
- 断网启动:有缓存时显示缓存且**不崩溃**;无缓存时显示错误页且**不崩溃**
- 断网时点播放:给出明确提示,不崩溃
- 从通知/锁屏触发下一集:确实切到下一集并继续播放
- 锁屏元数据:标题、副标题、封面非空

**纯逻辑仍走 JVM 单测:** 缓存的 stale-while-revalidate 顺序、离线态判定、排序筛选参数构造。

**流体云只能真机验收** —— 模拟器没有 ColorOS。测试覆盖到"通知内容正确"为止,
流体云表现列为用户手工验收项,**不得伪造结果**。

## 7. 验收标准

- **断网启动不崩溃**,有缓存显示缓存并提示离线;无缓存显示可重试的错误页
- 锁屏/通知显示正确的标题、副标题、封面,并有可用的上一集/下一集
- L3 路径下 seek 要么真的生效,要么明确禁用并告知 —— 不允许"假装成功"
- 首页结构对齐截图(浅色);「我的媒体」可进入各库
- 收藏、排序筛选、合集、已看标记可用
- 全部既有测试保持绿;新增端到端场景全绿
- 仓库任何位置(含历史)不含真实凭据
