# 播放进度上报生命周期 设计文档

> 状态:已定稿(2026-07-29)
> 前置:v5(播放页可读性 / 首页 inset / 下拉刷新 / 删除服务器 / 剧集顺序连播)已合入 master。
> 本文覆盖一个真机现场缺陷:**已播完的剧集在 Jellyfin 里仍带着进度条,赖在「继续观看」里不走。**

---

## 1. 现象与取证

用户在 PC 端 Jellyfin Web 上看到:某剧集的 E2、E3 **既有「已播放」蓝勾、又有进度条**,而且仍然出现在「继续观看」里。用户的第一判断是「客户端没把播完事件推给服务器」。

**这个判断是反的。** 蓝勾恰恰证明完播上报发出去了并且生效了 —— Jellyfin 只在收到位置 ≥ `MaxResumePct` 的 stop 上报时才打勾。真正的缺陷是:**打完勾之后,客户端又多发了一条带着旧位置的上报,把进度写了回去。**

### 1.1 服务端行为(在目标服务器上实测,非推断)

用 test 账号在空白剧集上做对照实验,结束后全部复原:

| 上报序列 | 服务端结果 |
|---|---|
| `stop` @99% | `Played=true`,`PlaybackPositionTicks=0` |
| ↑ 之后再来一条 `progress` @40% | `Played=true`,**位置变成 40%** |
| ↑ 之后再来一条 `stop` @40% | `Played=true`,**位置变成 40%** |
| `stop` @89.5% | `Played=false`,位置 89.5% |
| `stop` @90.5% | `Played=true`,位置归零 |
| `POST /UserPlayedItems`(markPlayed) | `Played=true`,位置归零 |
| 已 `Played` 的条目上再发 `start` @30% | `Played` **被清除**,位置归零(重看语义) |

**结论:** 能造出「蓝勾 + 进度残留」的只有一种情况 —— **条目已被标记播完之后,又收到一条 `progress`,或一条位置低于 `MaxResumePct` 的 `stop`。** `MaxResumePct` 实测为默认值 90。`start` 不是元凶(它会清除播放标记)。

### 1.2 客户端的三条肇事路径

**根因 A —— 补报队列重放没有时效判断(主因,且是必然发生的)**

上报失败会入队到 Room(`ProgressReportEntity`),等待重放。重放时机是 `PlaybackProgressCoordinator.onSourceReady`:**每次新的源就绪都 `flushPending()` 一次**。

自动连播时的实际顺序(`PlaybackService` 的 `STATE_ENDED` 监听器):

```
E2 播完 → sink.stop(E2 @100%)      → 服务端:E2 打勾、位置归零
       → 推进到 E3 → Ready(E3)
       → onSourceReady → flushPending()
                       → 重放队列里那条 progress(E2 @2分钟)
                       → 服务端:E2 位置变回 2 分钟,勾还在   ← 缺陷现场
```

`ProgressReportDao.pending` 是纯 FIFO(`ORDER BY createdAt ASC`),**没有时效上限、没有按条目去重、没有「这条记录是否已被更完整的事实取代」的判断**。

上报失败最常发生在每集**刚开播的几十秒**(endpoint 正在选路、正在拉流、`SessionJellyfinApi` 刚被 `invalidate`),这解释了现场残留的都是靠前的位置。

**根因 B —— 心跳与 stop 之间没有顺序保证(不需要任何失败即可发生)**

10 秒心跳的 `progress` 是一个挂起的网络请求。它在飞的这段时间里如果播放正好结束:

```
t=0    心跳读到 94%,请求上路
t=+2s  STATE_ENDED → stop(100%) 上路
t=+3s  心跳那条 94% 后到达      → 位置写成 94%,勾还在   ← 缺陷现场
```

两条请求各走各的连接,到达服务端的先后**没有任何保证**;代码里也不存在「这一集已经收尾,更旧的上报一律作废」这个概念。

**根因 C —— 协调器的可变状态缺少跨线程可见性(次要)**

`PlaybackService.onDestroy` 在 `Dispatchers.IO` 上调 `PlaybackProgressCoordinator.onPlaybackStopped`,而 `currentItemId` / `currentSessionId` / `lastKnownPositionMs` 都是普通 `var`,其余调用方全在主线程。两者之间没有 happens-before 边,IO 线程可能读到陈旧值而重复发一条 stop。

后果比 A、B 轻(重发的是接近 100% 的 stop,服务端结果不变),但属于同一处生命周期管理的漏洞,一并修掉。

### 1.3 为什么 Findroid / VidHub 没有这个问题

它们**没有离线补报队列**:上报失败就丢弃,不留、不重放。JellyCast 为了「断网也不丢进度」加了队列,但只实现了「重放」,没有实现「重放前判断这条还算不算数」。

### 1.4 现有测试为什么没抓到

`PlaybackProgressCoordinator` 有 17 个用例、`ProgressReporter` 有 10 个,全绿。**没有任何一个断言「已经收尾的条目不许再被写入」。** 其中「每次源就绪都顺带排空一次本地补报队列」这条,恰恰把出问题的行为固定成了正确行为。

## 2. 设计

### 2.1 核心规则

> **一个条目的上报生命周期以 `stop` 终结。此后任何更旧的上报一律作废 —— 不发出、不入队、不重放。**

### 2.2 落点:`ProgressReporter` 作为唯一收口

实时上报与队列重放**都**经过 `ProgressReporter`(它同时实现 `ProgressSink` 并持有补报队列),因此它是唯一能看到全部上报的地方,规则放在这里不会有旁路。

`PlaybackProgressCoordinator` 继续只负责「什么时候该报什么」,不感知终结规则 —— 两者的职责边界不变。

### 2.3 三条子规则

**规则 1 —— 终结标记**

`stop(itemId)` 被调用时(无论实时成功还是入队),把 `itemId` 标成已终结。此后:

- 该条目的 `progress` 直接丢弃(不发、不入队)
- 该条目的 `stop` 仍然放行(幂等重发无害,且 `onDestroy` 的兜底 stop 必须能过)
- `start(itemId)` 清除该条目的终结标记 —— 与服务端的重看语义一致(§1.1 末行)

**规则 2 —— 入队清理**

发出 `stop(itemId)` 之前,先删除补报队列中该 `itemId` 的**所有**既有记录。

这条保证:**持久队列里不可能残留「已终结条目的旧心跳」**。因此终结标记不需要持久化 —— 进程重启后队列本身已经是干净的。

需要给 `ProgressReportDao` 增加一个按 `(serverId, itemId)` 删除的查询。这是纯新增查询,不改表结构,**不需要 Room 迁移**。

**规则 3 —— 全序**

所有上报(实时 + 重放)串行经过同一把互斥锁,每次只持有**一个 HTTP 调用**的时长。

这保证「在飞的 `progress`」必定先于随后的 `stop` 到达服务端,而不是靠运气。与规则 1 叠加后,根因 B 的两种交错都被覆盖:

- `progress` 先拿到锁 → 它先落地,`stop` 随后落地 → 终态正确
- `stop` 先拿到锁 → `progress` 随后被规则 1 丢弃 → 终态正确

**已知取舍:** 一次实时 `stop` 最多等待一个在飞请求的时长(受 OkHttp 超时上界约束)。补报重放必须**逐条**获取该锁而不是整批持有,否则一次满队列(上限 100 条)的重放会把实时 `stop` 堵在后面。

### 2.4 终结标记的存储

进程内的有界 LRU,容量 32 条,不引入 Room 迁移。

容量足够的理由:标记只需覆盖「刚 stop 的条目仍可能有在飞/排队的上报」这个窗口,窗口长度是秒级;32 条远超任何真实的并发播放条目数。溢出时丢弃最旧的标记 —— 那些条目的窗口早已关闭。

### 2.5 根因 C 的处理

给 `PlaybackProgressCoordinator` 的可变状态加一把 `Mutex`,让 `onSourceReady` / `onTick` / `onPlaybackStopped` 三个入口互斥。这同时消除了跨线程可见性问题和「stop 幂等」判断本身的竞态。

## 3. 范围

**做:** 终结标记 · 入队清理(含新增 DAO 查询)· 上报全序 · 协调器状态加锁 · JVM 单测 · 真服务器 E2E 验证

**不做:**

- **「下一集」按钮在接近片尾按下不会打勾。** `onSourceReady` 的换条目分支用 `lastKnownPositionMs`(最多慢 10 秒的心跳位置)给上一条目补 stop;在 91%~100% 之间按下会报出低于 90% 的位置,于是不打勾。这是相邻但**独立**的缺陷,根因不同(位置来源不准,而非生命周期),单独立项。
- 弹幕渲染 · 深色主题 · 改播放页形态 · 离线下载

## 4. 测试策略

### 4.1 JVM 单测(`:core:player`)

覆盖三条子规则各自的行为,以及它们的组合。关键用例:

- `stop` 之后同一条目的 `progress` 不发出、不入队
- `stop` 之后同一条目的 `stop` 仍然发出(幂等)
- `start` 清除终结标记,之后的 `progress` 恢复正常
- `stop` 会删除队列中该条目的既有记录
- 终结标记不影响**其它**条目
- 重放逐条获取锁,不整批持有
- 协调器三个入口互斥

### 4.2 真服务器 E2E(决定性证据)

**JVM 单测证明不了这个缺陷已修复** —— 缺陷的判据在服务端的 `UserData` 上。沿用 v4 立下的铁律(依赖平台/外部系统行为的部分必须在真机上跑过),新增一个 E2E:

1. 预置一条陈旧的 `progress` 记录进 Room 补报队列(指向待测剧集,位置取靠前的值)
2. 让这一集真的播放到结束 —— 用 `AudioPlaybackEngine.seekTo(runtime - 15s)`;转码流按 `startTimeTicks` 重新起流,十几秒后自然进入 `STATE_ENDED`
3. 等待完播上报与随后的连播落定
4. 通过 Jellyfin API 断言该集的 `UserData`:**`Played == true` 且 `PlaybackPositionTicks == 0`**
5. 无论成败都复原该集的 UserData

**这个测试在修复前必须是红的** —— 它就是 §1.2 根因 A 的自动化复现。

E2E 使用 `testing.properties` 里的测试账号(已 gitignore),凭据不进版本库、不进文档。

## 5. 验收标准

- 一集正常播完后,Jellyfin 里 `Played=true` 且**不再出现在「继续观看」**
- 断网期间播完一集,恢复联网后补报**不会**把进度写回已播完的条目
- 播放结束前一刻的心跳不会覆盖完播状态
- 新增 E2E 在修复前红、修复后绿
- 既有全部 JVM 单测保持绿
